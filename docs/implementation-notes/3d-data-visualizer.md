# 3D and 2D visualizer

## Intention

Replace the legacy retention time/m/z 3D plot with a reusable viewer for intensity over two numeric coordinates. Built-in sources cover LC-MS, one ion mobility frame, and imaging pixels. Multiple samples and multiple extracted m/z ranges must remain comparable in the same physical coordinate system, and rotating, zooming and hovering must stay fluid for large surfaces.

## Decisions

- Replaces the former `fx3d` 3D plot, which was removed with its only helper `SliderCell`. Menus, the batch module list, the main window action, and feature-table actions open `IntensityMap3DModule`; all entries are named "3D visualizer" (user request). The old module is registered in `ModuleMappingUtils.getRemovedModules()`, so batch files with a 3D plot step drop it with a warning instead of failing.
- The 2D visualizer (`IntensityMap2DModule`) replaces the former 2D plot (`twod`, removed and registered in `ModuleMappingUtils`) and opens the same tab as a 2D view (user request). It shares the parameter class but stores its own settings, and it adds 2D maps of ion mobility frames and imaging data. The former plot's feature markers from a feature list were dropped (user decision). It also replaces the image viewer module (`ImageVisualizerModule`, user request, registered in `ModuleMappingUtils`): double-clicking an imaging file, the raw data and visualization menus, and the feature table "Image" action open the 2D visualizer. The image chart `ImagingPlot` stays for the views that embed it (co-located images, image all MS/MS, timsTOF MALDI MS/MS scheduling) and normalizes like the feature table images through the image normalization preference, since the viewer's parameters are gone. The viewer's optional mobility range and raw file info panel have no counterpart.
- The two views are the two implementations of the sealed `IntensityMapProjection` in `data`: `IntensityMapPerspective` (3D) and `IntensityMapTopView` (2D). It lives in `data` so that `render` and `plot` can use it without a dependency cycle, so it only states properties (label, heights, rotation, lighting, depth test, fixed plot area, physical pixels, default angles, sampling density); algorithms that differ, mesh building and picking, are exhaustive switches over the projection in `render`. There are no boolean 2D flags.
- The 2D view stays in the 3D engine (user decision) instead of a JFreeChart heatmap, so overlays, side by side, the spectrum and chromatogram panes, hover, and zooming behave the same. The camera looks straight down and cannot rotate: a plane facing a perspective camera projects without distortion, so the view is a true 2D map. All values lie in the plane without any height (user decision), intensity is only shown by color; hover picks the overlay drawn last with signal at the cursor instead of ray marching heights. Non-pixel data are drawn as flat cells instead of a surface (user request): every value fills the space halfway to its neighbors, so consecutive scans touch at any zoom, like the nearest scan fill of the former 2D plot; a surface interpolates between vertices and fades to the floor between scans with and without signal. Neighboring cells share corner points, so cells need no more vertices than the surface. The 2D view samples one bin per logical pixel of its actual plot area (`IntensityMapTopView`), like the former 2D plot, which computed the maximum raw intensity of every pixel on each redraw (user request: the first version sampled too coarsely): cells thinner than a pixel are not drawn, so centroids jittering between fine m/z bins, or bins of one physical pixel on HiDPI screens, appeared as dashed traces. Zoom windows get the same resolution in their margin, and the 2D view reads the window again as soon as its bins get coarser than 1.25 screen pixels. Zoomed 2D windows must be as fine as the zoomed out view (user report: partial zooms looked coarser than zoomed out, about 0.5–0.65 bins per pixel). The 2D budget counts bins instead of surface vertices (up to 4 M bins, about 32 bytes each), since flat cells only become geometry where a value is measured; the 3D surface keeps its vertex budget. A 2D window samples the screen size of its overlay with a 25 % margin and has the whole budget of its overlay, and it is merged with the complete base. A first version shrank the base around the window to a quarter of its bins instead of raising the budget and used a 10 % margin; panning then revealed large blocks and zooming out showed them over the whole view until the next read (user report with a screen recording), so that was dropped. Zooming out shows the base at once instead of after the view has settled. Panning in 2D must not show coarse strips (user request): the view is checked every 150 ms while it moves instead of only after it has settled (3D still waits 300 ms for the view to settle, reading and rebuilding surfaces while rotating would stutter); a running read of a part in view finishes instead of restarting on every move, and the view is checked again when it arrives; a new window is merged into the data shown so far, so parts read before stay sharp (until the kept data exceed 4 M bins per overlay, then the base is used again); and the window reaches half the visible size ahead in the pan direction and a tenth behind, instead of a quarter on each side. Every overlay has its own visible part and window (user report: scrolling or zooming out side by side showed every tile at base resolution): with parts of neighboring tiles on screen, e.g. the right edge of one sample and the left edge of the next, the union of their visible parts spans nearly all data and counted as zoomed out. The plot reports the data window and screen size of each overlay in view, the loader reads all needed windows in one task, in parallel per file, and a 2D overlay only shows its base if the base has enough bins for its screen size, since a nearly complete tile can be larger than the base was sampled for after zooming in side by side. Colors are the only cue of intensity in 2D, so they follow the transformation (default log10, chosen after testing; square root and log2 selectable). The paint scale is the same as in 3D (user decision after testing: a low end that faded into the plot background, like the white start of the former palette, did not look good). In 2D and 3D the paint scale starts at the noise floor instead of zero (user request): with log10 colors and the default cut-off, shown values otherwise started at about 60 % of the scale and never used its lower colors. This is part of the scale, not of the color range handles, so user ranges are kept; legend and range labels show the cut-off intensity as lower end. Images are colored in 2D like in 3D (user request after a first attempt to start log10 colors at the weakest pixel): the 2D view of images starts with a linear transformation, so its colors are linear from the noise floor like the colors of the 3D view, whose transformation only changes heights. LC-MS 2D views keep log10 colors by default. The 2D view uses a lower noise floor by default (0.05 %, chosen after testing) and skips measured zeros, which would cover the floor with the lowest color of the paint scale. The former plot also normalized its colors to the maximum of the visible area on every zoom; the 2D view keeps the shared intensity scale, the color range handles clip it. Floor, grid, hover cursor, and the slice line lie in the data plane; a slice plane reaching up to the data projected into a wide band when the camera is close in a deep zoom. Floor and grid lie in the data plane, lifted they project slightly smaller than the data in the perspective top view, so cells at the data edge stuck out. Zooming in resamples finer as in 3D, and only an ambient white light is used, so colors match the paint scale without shading. All geometry lies in one plane, so the model disables the depth test and draws in child order (axes, surfaces, markers, zoom box): coplanar geometry otherwise flickers, and the zoom box stays on top of the data (user request). The axes stay at a fixed plot area, like a zoomed chart (user decision): the fitted view defines the area, zooming and panning only change the tick values, and data outside the area are clipped instead of covering the tick labels. The area is stored as margins to the viewport edges, so it follows resizing; the viewport has the scene background, so no other color shows around the clipped area. Only a single plot has a fixed area: overlay, a focused tile, or a side by side tile that fills the plot area after zooming in (user request, revising the first decision that unfocused tiles always keep their axes at the data edges). The zoomed tile gets the plot area a fitted single plot has, computed by fitting the camera to the tile and restoring it; a tile only counts if it covers the whole plot area, otherwise the axes would frame data that do not reach the plot edges. Zoomed out, the axes return to the data edges of every tile, like in 3D. A double-clicked tile keeps its fixed plot area only while it fills it as well (user report: after focusing one image and scrolling, the clip of its plot area cut off all other tiles); zooming out or scrolling beyond it ends the focus. A tile counts as filling the plot area with a tolerance of one pixel, since a fitted tile ends exactly at its corners. Changing the layout fits the view again, since the tiles change. The axes are framed by the part of the floor seen through the plot area, marker and axis lines scale with the zoom, and a zoom box fills the plot area instead of the viewport. Dragging and arrow keys pan. The camera presets, height, transformation, and height baseline are hidden because they only change heights.
- Packages: `intensitymap` holds the modules, parameters, tab, and the loading of sampled data (`IntensityMapDetailLoader` for the base and zoom window, `IntensityMapSamplingTask`, which reports through a listener instead of touching the tab); `data` the numeric model (grid data, bounds, detail, region, series, smoothing); `sampling` raw-data extraction and overlay layers; `spectrum` the spectrum lookup and pane; `render` geometry and picking without UI controls (mesh, scale, picker, tiles, screen outlines); `plot` the reusable JavaFX plot. `IntensityMapPlot` owns the scene and the overlay states and coordinates package-private parts with one job each: camera and navigation, the fixed 2D plot area, the zoom box, hover and markers, materials, toolbar and Display controls, tile layout with axes and titles, and the background mesh builder. All classes carry the `IntensityMap` prefix (user decision, mzmine style). `render` and `data` do not depend on `plot`.
- Opened from selected features, the visualizer shows one overlay per feature m/z range for every raw file of the selection (user request); overlapping ranges, such as one row in several samples, are merged. The scan selection is limited to the features' retention time range except for imaging, and to their polarity if they share one, and the data dimensions are chosen automatically. These settings apply to a copy of the module parameters, so they never become the defaults of the module dialog. A file without scans matching the scan selection is skipped with a status message instead of failing all samples.
- Imaging ignores the retention time filter of the scan selection in sampling and spectrum lookup: pixels have no meaningful retention time (imzML stores 0), so a range left from LC-MS data excluded every pixel. The shared m/z range parameter component is left unchanged (user decision).
- Imaging files always resolve to the imaging view (a mobility frame only when explicitly requested for ion mobility imaging); other files never resolve to imaging. A stored LC-MS mode otherwise made imaging data unusable. Automatic mode selects imaging for imaging files and LC-MS otherwise. Mobility frame mode is explicit. Overlays require matching dimensions and units.
- Axes: LC-MS shows retention time on x and m/z in depth. Mobility frames show m/z on x and mobility in depth (user request, matches the usual IMS heatmaps); the sampler builds (scan coordinate, m/z) grids and transposes them, and zoom windows are interpreted in displayed coordinates.
- An overlay (`IntensityMapLayer`) is one raw file plus one m/z extraction range with a stable id and color. Each file starts with one all-m/z layer. Entering m/z values or ranges in the side panel adds one layer per file and range and replaces that file's all-m/z layer, which would otherwise dominate the shared intensity scale. Files added later receive the same extraction ranges. Removing a file's last layer removes the file from the tab.
- All layers of one file are read in a single pass over its spectra. Spectra are sorted by m/z, so only each extraction window is visited. Files are sampled in parallel. Sampled layers are cached by id: adding or removing overlays only reads new layers; existing layers are max-pooled in memory to their new share of the budget.
- Narrow m/z windows limit the number of m/z bins: at least 5 ppm for centroid data, and 1.5× the median profile point spacing for profile data. Finer bins only create jagged ridges or comb artifacts.
- Sampling follows viewport size, display scaling, and zoom, but the total vertex count across all overlays is bounded by a render budget (`IntensityMapDetail`: 1 M surface vertices, 360 k pixel columns) plus a memory guard. Zooming replaces the former region selection, which users did not expect (user decision): like the former 2D plot, the user just zooms further, in 2D and 3D. Ctrl/⌘ + drag on the floor zooms to the dragged box. The coarse full-range data of each layer stay as base; when the view shows less than 90 % of the floor, only the visible window plus a 25 % margin is read at full budget and merged into the base (`IntensityMapGrid.merge`), so the data keep their bounds and the camera does not jump, and the surroundings stay visible while panning. Merged grids have mixed resolution, so cells carry explicit extents. Reading is expensive, so repeated drawing is prevented (user request): requests are debounced (300 ms), only one window read runs and a newer request cancels it, a window is kept while it covers the view and the view is not much smaller than it (40 % in 3D, about one bin per pixel in 2D), and zooming out to nearly all data shows the base again without reading. Only overlays in view are read (user request): visible ones, and side by side only those whose tile is on screen, so zooming into one of many samples reads one file. Every layer keeps its own window, so panning to another tile reads only that file and layers whose window still covers the view are not read again; hidden overlays are read once they are shown. The render budget of the window is shared by the overlays in view only. Every layer keeps its last three windows (merged with the base), so zooming back into a region seen before shows it again without reading (user request); a new base clears them, since they contain the old base. The first base is read once the plot is laid out, and the base is read again whenever the zoomed out view needs 25 % more bins along an axis than it was sampled with, e.g. after enlarging the window; before, a 2D view sampled before its first layout kept a base of 100 × 100 bins, so zooming out looked much coarser than zooming in. The previous surface stays visible while replacement data loads. The zoom depth is only limited by a minimal camera distance (user request: a 6× limit was far too shallow); near and far clipping planes follow the viewed distance, and axis and marker lines get thinner with the visible range so they do not cover zoomed data.
- LC-MS uses only the scans of the lowest MS level in the scan selection (usually MS1), also for the spectrum lookup (user request): scans of another MS level, e.g. MS2 scans of DDA data, are no zeros between the scans of a trace, and as retention time columns they broke every trace into dashes.
- LC-MS and mobility retain native, potentially irregular coordinates while they fit the budget. Larger inputs are reduced to existing coordinates, with maxima retained within bins to preserve narrow signals. Interpolation connects measured spectral rows; no duplicate rows are manufactured.
- Imaging sums the selected m/z intensities per pixel and retains maxima when spatial bins are combined. Pixels are merged in whole blocks on the acquisition grid (factor × pixel step), both when sampling and when shrinking existing overlays; picking every n-th coordinate left irregular spacing, and the resulting gaps and exposed walls showed as grid lines once many m/z overlays shared the budget. Imported coordinate origins are used verbatim. Metadata provides physical pixel sizes; absent metadata uses pixel units. Unmeasured cells have no geometry, whereas measured zero-intensity pixels remain represented. Pixel columns only draw walls that can be visible (neighbor missing, separated, or lower).
- Overlay layouts: coincident surfaces of similar samples fight for depth (flickering color stripes) and JavaFX has no order-independent transparency, so opacity cannot resolve them. "Overlay" keeps all surfaces in place with a tiny per-overlay lift so ties resolve consistently. Opacity only applies there, with more than one overlay (user decision): all overlays start at the same opacity, and side by side tiles stay opaque, so the slider is disabled there. "Side by side" places visible overlays as uniformly scaled tiles in one scene, so rotation and zoom stay linked and meshes are reused. Every tile has its own axes (user request). Columns and rows are configurable (Auto gives a near square grid; rows are added if too few). Side by side becomes the default once more than one overlay is shown, unless the user picked a layout.
- A "Blend colors" layout (one composite surface mixing up to three overlay colors by intensity ratio) was removed with its composite and mixing code (user decision). Color changes in the panel propagate to the tab's layers and the spectrum.
- The feature table's "Co-located images" opens the 2D visualizer (user request) instead of its own grid of image plots, whose classes were removed: the selected feature's image and those of its co-located features (MS1 feature correlation) side by side in the selected feature's imaging file, most similar first, without the module dialog. Overlapping m/z ranges merge at the position of their first appearance, so the order of similarity is kept. The spectrum marks all m/z ranges, and the feature list names the images.
- Opening a viewer from the feature table (2D, 3D, or "Image") shows all raw data files of the feature list side by side (user request), not only the files of the selected features, so the samples can be compared. The setup dialog still lists the files and may deselect some. The m/z overlays and the retention time range span the features of the selected rows in all files, since aligned samples are shifted slightly; overlapping m/z ranges merge. Several overlays switch to side by side on their own, as long as the user has not chosen a layout.
- Side by side tile titles omit parts shared by all tiles: the file of several m/z overlays, and the prefix and suffix shared by file names (cut at separators), while m/z descriptions stay complete. They are placed in screen space above or below the projected outline of their tile including its signal, truncated to the tile width, and hidden when they would cover another tile outline, an axis label, or a title. "Show labels" in the labels menu at the top right hides all text (tick labels, axis titles, tile titles, peak labels); the camera then reserves no room for labels.
- Peaks can be labeled with the features of a feature list (user request), in 2D and 3D. Images get no peak labels (user decision); with a chosen feature list, the known annotations of the features inside the m/z range of an image overlay form a second, centered title line below the m/z and extraction window instead (user request; on one line they were cut off in narrow side by side titles), e.g. "m/z 760.5851 ± 5 ppm" above "PC 34:1 [M+H]+": compound name or preferred annotation name with the ion notation, strongest feature first, two names and the rest counted; unannotated features add nothing, and the complete m/z range gets no annotations. The feature list is chosen like for peak labels; the search field and "Annotated only" only apply to peak labels and are hidden for images. Opened from the feature table, the feature list of the selected features labels the peaks; the labels menu has an explicit "Feature list: <name>" submenu (user request) with none and every project feature list containing a shown file, says so if there is none, and replaces the choice with a note for images; "Annotated only" hides labels without an annotation. A label shows the preferred annotation name or the m/z, followed by the ion notation if known (user request: adduct of the preferred annotation, else the best ion identity). The compound grouping of the feature list is used (user request): a compound gets one primary label with its name at its representative ion, its other ions get secondary labels with only their ion notation (or member role), and the hover readout names the compound. Labels sit at the feature apex (RT and m/z, or m/z and mobility for frames of features eluting in the shown frames), in 3D on top of the drawn surface, which may be higher than the feature. They are placed in screen space after the axis labels, primary before secondary and strongest first; a label is hidden when its marker or all three candidate positions (above right, above left, below right) overlap placed text or leave the plot area, when a surface covers it in 3D, or when the peak lies below the noise cut-off. At most one label per 100 × 80 px is shown, so the labels do not bury the data; zooming in makes room for more.
- A search field next to the labels menu (user request, like the annotation search of the network visualizer: substring match with autocompletion of annotation and compound names) shows only labels whose name, text, or description contain the text, ignoring case, so it also finds ions and m/z values. Searched labels are not limited by the label density, only by overlaps.
- GC-EI deconvolution keeps one feature per compound and stores the grouped features only as a GC-EI pseudo spectrum (m/z and heights at the feature retention time). Their signals are read from that spectrum (user request): the hover highlight marks them like grouped features, and the label description counts them. Other pseudo spectra, e.g. of LC-DIA, hold fragments that are not signals of the MS1 map and are ignored.
- Hovering a label highlights its group (user request): solid rings mark the features of the same compound in the same overlay, also those whose labels do not fit, and their shown labels get an accent outline; dashed rings mark the other isotopes of every feature of the group, the hovered one and its grouped features alike (user report: the isotopes of grouped features were missing), from their isotope patterns (of the feature, else of the row) inside the overlay's m/z range, at the feature's RT or mobility, scaled to the feature height at the pattern signal closest to the feature m/z. Correlation row groups are not reachable from rows any more, so features without a compound are grouped by their ion identity network. Highlights skip the occlusion test. While a label is hovered, a veil in the plot background color (70 % opaque) covers the rest of the data, with rounded openings around the screen extent of every highlighted peak (its RT or mobility and m/z range, in 3D from the floor to its apex; isotopes and deconvolution ions use the extent of the labeled feature), and the other labels fade to 30 % (user request: the peaks of the group should stand out). The veil is drawn in screen space, so it needs no mesh rebuild and works the same in 2D and 3D.
- Clicking a label moves the camera onto its feature (user request), like a zoom box around the feature extent (RT or mobility and m/z range of its raw data points) padded by 1.5 extents on each side, and at least a share of each axis: 1 % in 2D, where isotopes stay in view, 8 % in 3D, where a smaller share only showed the flank of the peak up close with surrounding signals in front of it. In 3D the box includes the peak top. The camera flies there like in a movie instead of jumping (user request): it pulls back while panning and pushes in on the feature, the smooth zooming and panning path of van Wijk and Nuij (ρ = √2, as in d3 and map applications), eased at both ends and lasting 0.7–1.8 s by path length. Axes and labels follow every frame; the detail of the target is read on arrival. Any mouse press, scroll, pinch, or key stops the flight where it is, so the user can take over. Zoom boxes still jump, a dragged box should respond immediately. The click does not select a spectrum, and double-clicking a label does not reset the view. Labels stay mouse transparent; the plot hit-tests them itself, so dragging, scrolling, and hovering work over labels.
- Optional Gaussian smoothing over neighboring data points (radius in points, both axes or one) runs in the background with normalized convolution, so unmeasured cells stay unmeasured and do not pull neighbors to zero. The displayed overlays keep their ids; surface, picking, hover values, and the shared intensity scale all use the smoothed values, and the readout marks them as smoothed. Results are cached per overlay and smoothing parameters.
- A noise floor (percentage of the maximum, default 0.1 % in 3D, 0.05 % in 2D, and 0 % for imaging data in both (user request), slider plus number field) removes geometry of quiet cells, e.g. the noise carpet of many overlaid samples. It is part of the mesh cache key.
- Coloring by overlay uses flat overlay colors for LC-MS and frames, where height shows intensity. Imaging overlays and all overlays of the 2D view instead shade from the background to their color by intensity (user request): log transformation and the minimum height compress pixel heights too much to read intensity differences, and the 2D view has no heights. This follows the single color heatmaps of mzmine (`IonMobilogramTimeSeriesToRtMobilityHeatmapProvider`), which fade into their black 2D background; here the gradient starts at the background color (white or black in the first version, user decision). A transparent start looked washed out and showed depth sorting errors between pixel columns. Colors too close to the background, e.g. yellow on white, end on a shade further from it, so low intensities always show the background color. The gradient follows the linear color scale, so it respects "Each overlay to its maximum".
- Every overlay has its own color range (user decision, like the ion image sliders of SCiLS Lab): a color bar with two handles in its panel row clips the colors, so weak overlays can be brought out next to strong ones. Meshes store the linear color position of every value as texture coordinate, so clipping only replaces the texture of the overlay (values below the range get the first color, above it the last) and needs no resampling or mesh rebuild. The range is kept while resampling, shown in intensities of the overlay, and only offered when colors show intensity (paint scale, or overlay gradients); flat overlay colors of 3D LC-MS data have none.
- By default all overlays share coordinate bounds and one intensity scale. Visibility and opacity changes do not renormalize. "Each overlay to its maximum" scales each overlay to its own maximum; with normalized logarithmic heights there is no common numeric intensity axis, so only the axis title is shown.
- Intensity transformation and normalization reuse the imaging preferences (user request). In 3D they are offered for imaging data only; other data always use linear heights and no normalization (user decision: log heights make no sense for chromatographic data). In 2D the transformation applies to the colors of all data, see above. Imaging starts with a log10 transformation and the minimum height (user decision): `PaintScaleTransform` (linear, log10, log2, sqrt) transforms only the height, offset by one so zero stays at the base; colors stay linear, which reads better than transformed paint scales (user decision); the default is the image transformation preference. `ImageNormalization` (average TIC) uses the same per-scan factors as the imaging code (`ImageNormalization.scanFactors`, `IonTimeSeriesUtils.averageTic`/`ticFactor`); it applies per scan, mobility scan, or pixel, relative to the complete scan selection so zoom windows keep their values, and requires resampling. The default is the image normalization preference. The noise floor stays a linear fraction of the maximum.
- Imaging heights start at the lowest shown pixel by default (user request, Display option "Start at the lowest pixel"): with log heights the weakest pixels otherwise reach most of the height and form a tall base. The baseline is the weakest pixel of all overlays relative to the maximum, at least the noise floor because lower pixels are not drawn; it is stored as a fraction of the maximum, so it also applies to overlays scaled to their own maximum. Values at the baseline keep 2 % of the height, since pixel columns without height are not drawn. The intensity axis uses the same mapping and has no ticks below the baseline.
- Meshes use `VertexFormat.POINT_NORMAL_TEXCOORD` with normals computed off the FX thread, because JavaFX smoothing groups are evaluated on the render thread. Only vertices referenced by faces are kept. Meshes are rebuilt only when the data instance or its geometry-relevant scale changes, on a small thread pool, and stale builds are cancelled through a generation counter.
- Meshes, axes and markers are mouse transparent. JavaFX picking tests every triangle on every mouse event, including drags; hovering instead ray-marches the sampled height fields (`IntensityMapPicker`). The hover readout lists all visible overlays at the hovered coordinate.
- The reusable `IntensityMapPlot` accepts lists of `IntensityMapSeries` built from numeric `IntensityMapGrid`, independently of raw files. Features like m/z entry, removing overlays and adding files only appear when the owner registers a listener; resampling for the zoom window is requested through a detail listener. Theme colors are pushed by the owner via `setDarkMode`, so the plot does not depend on the mzmine configuration.
- Axis titles format units with the unit style of the preferences (e.g. "Retention time / min"), like other mzmine charts.
- Axis labels use round tick steps and are hidden for axes that are strongly foreshortened in the current view. Tick counts follow the projected axis length, so zooming adds or removes ticks. Tick labels and axis titles are placed in screen space, a fixed distance outside the axis line, so they never reach into their own plot regardless of tile size. Tick labels use the preference number format with only the decimals the tick step needs. Labels not fully inside the clipped viewport are hidden. One placement pass per frame shows tile titles first, then axis titles, then ticks, and hides any label that would overlap a placed label or another tile's outline (layout bounds, not bounds in parent, which include text rendering margins). Displayed numbers (ticks, hover readout, legend, overlay and spectrum descriptions) use the mzmine number formats from the preferences by axis kind (RT, m/z, mobility, intensity); the plot falls back to round-step formatting without preferences.
- The paint scale is chosen in the viewer only, the module has no paint scale parameter (user decision). It starts with the default paint scale of the preferences, like other mzmine heatmaps, and the selector lists all paint scales of the preferences, including custom ones.
- Mobility frames are chosen in the visualizer, not by a frame number parameter (user request): a base peak chromatogram of the frames (`TICPlot`/`TICDataSet`, as in the ion mobility raw data overview) replaces the spectrum pane. The module m/z range limits it; overlays do not change it. A click shows the frame closest to that retention time, Ctrl/⌘ + drag averages all frames of the dragged range (user request; the overview's frame merging with averaged instead of maximum intensities, signals required in up to five mobility scans). A range with at most one frame shows the frame closest to its center. The view starts with the most intense frame of the first file; overlaid files show their frame closest to the same retention time or their own average of the range. Averaged frames are cached (last four) because zooming resamples; the cache belongs to one visualizer, so closing it releases the frames. Frames of different polarity or MS level cannot be averaged and are reported like missing scans. Frames have no spectrum pane, so m/z overlays are entered in the side panel.
- A spectrum pane below the 3D view shows one spectrum per selected position: the closest RT scan for LC-MS or the pixel for imaging. A plain click in the 3D view selects the position. A light slice marks the position a click would select, only while hovering (user decision: a persistent marker was too heavy): an RT plane for LC-MS and one plane along x and one along y for imaging. Planes reach just above the highest data point of their tile and carry accent lines on top and at the floor, so the crosshair stays visible above dense pixel columns (user request). The initial position is the global intensity maximum. With several files, their spectra at that position are overlaid.
- Following the image viewer, a click on a spectrum signal replaces all m/z overlays by the tolerance window around the local apex, for every file. Ctrl/⌘ + click adds a range, or removes it if the click falls into an already selected range. Ctrl/⌘ + drag adds the dragged m/z window as an extraction range (user request, the same gesture as the frame range in the chromatogram of mobility frames; Ctrl/⌘ keeps its meaning of adding). Both panes share the gesture (`IntensityMapRangeDrag`); a press without movement stays a click. Removing the last m/z range of a file restores its all-m/z layer, whereas the remove button on an overlay card removes the sample. "All m/z" restores the default layers. Selected ranges are marked in the spectrum.
- Navigation: the mouse wheel and pinch zoom at the cursor (the camera moves along the cursor ray), Ctrl/⌘ + drag zooms to a box (a box of a few screen pixels is a click), trackpad two-finger scrolling pans, and double-clicking a side by side tile fits the camera to it (double-click elsewhere or R fits all), so single tiles can be inspected.
- The UI is compact (user request): one toolbar row with icon buttons for the camera presets, a "View mode" menu button for the layouts, a Display popover, and the noise floor. The front and side profile buttons show a peak for retention time or mobility and a spectrum for m/z axes, so their icons swap for IMS frames; imaging data have no profile views. The spectrum is a collapsible section below the 3D view (a custom header row with the shown position on the left and the usage hint on the right; a titled pane with a width-bound header graphic caused a layout feedback that grew the panel on every pass) and the overlay panel collapses sideways to a titled strip, instead of show/hide buttons (user request). The Display popover only lists options that apply: transformation and TIC normalization for imaging data only, overlay scaling and coloring with several overlays, the paint scale, and the tile grid size only for side by side. Styling sits at the top right next to saving (user request): the plot background color (theme default or the mzmine color picker; fixed white and black entries were removed, user request), grid lines, and the labels menu (user request: one menu that hides all text and chooses the peak labels). Axis, grid, and label colors follow the brightness of the background, and the floor is a slightly shifted background. The side panel has one row to add m/z values, one row per overlay (color, visibility, the sample name wrapped over several lines with the m/z extraction below in a smaller font instead of one truncated line (user request), a color range, options menu with opacity, show only, remove; also on right click), two header buttons, "m/z" to show all m/z and a file icon to add the raw files selected in the project (user request; an option to align m/z ranges on a Δm/z axis was removed).
- Raw sampling and mesh building have separate cancellation lifetimes owned by the tab/plot. Closing the tab stops both. The tab context menu removes tabs without a close event, so the tab holds no strong references from shared state: the dark mode listener is weak and idle mesh threads end. The module keeps no static mutable state. The module requires JavaFX 3D support.
- Entry points of the main window (raw data list menu, double-click on imaging files) capture the raw data files selected at the click and run the module on a copy with exactly these files (user report, twice: imaging files appeared next to selected LC-MS files). The stored parameters keep a new "As selected in main window" selection, so the menu and later runs follow the selection; files chosen differently in the dialog win. A stored file selection keeps the files of its last evaluation (e.g. the check when the dialog closes), copies keep them too, and changing only the selection type does not clear them, so reusing the stored selection opened files selected earlier.
- Changes outside the module are limited to replacing the former 3D plot, 2D plot, and image viewer and to reuse: the average TIC of `IonTimeSeriesUtils` and the per-scan factors of `ImageNormalization` (same normalization as images), the paint scale list of the preferences, and the color picker of the raw data list (`ColorPickerMenuItem`, palette swatches plus mixer) for overlay colors, which now also closes when placed directly in a context menu.
